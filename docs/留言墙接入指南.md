# 留言墙接入指南

## 先说结论

GitHub Pages 只能托管**静态文件**，它没有数据库、也不能执行你的后端代码。
所以「访客留言 → 我审核 → 公开显示」这件事，必须借一个外部服务来存数据。
本站已经把这个后端做成了**可插拔**的，你只要换三行配置，前端不用改。

推荐顺序：

| 方案 | 访客要不要登录 | 你审核的方式 | 成本 | 推荐度 |
|---|---|---|---|---|
| **A. Supabase** | 不要 | Supabase 后台点一下 `approved` | 免费额度足够 | ★★★★★ |
| **B. Giscus** | 要 GitHub 账号 | GitHub Discussions 里回复/隐藏 | 免费 | ★★★☆☆ |
| **C. 本机演示模式** | — | 无需，数据只在你自己浏览器 | 免费 | 仅用于试样式 |

国内访客大多没有 GitHub 账号，所以**推荐 A**。

## 方案 A：Supabase（推荐）

### 1. 建项目
1. 打开 https://supabase.com 注册（可用 GitHub 登录），新建一个免费项目。
2. 记下项目地址和公开密钥：**Settings → API**（新版界面叫 **API Keys**）里有
   - `Project URL`，形如 `https://xxxxxxxx.supabase.co`  
   - 公开密钥。新版形如 `sb_publishable_qghX8...`，老版形如 `eyJhbGciOi...`（anon public）。
     两种都能用，前端不用区分。

> 公开密钥是**设计上可以公开**的，它会写进前端。
> 真正的防线是下面的 RLS 行级安全策略，不是把这个 key 藏起来。

### 2. 建表 + 加审核策略
在 **SQL Editor** 里整段执行：

```sql
create table public.messages (
  id         bigint generated always as identity primary key,
  name       text        not null check (char_length(name) between 1 and 20),
  body       text        not null check (char_length(body) between 1 and 200),
  approved   boolean     not null default false,   -- 默认待审核
  created_at timestamptz not null default now()
);

alter table public.messages enable row level security;

-- 任何人只能读到已通过审核的留言
create policy "public read approved"
  on public.messages for select
  using (approved = true);

-- 任何人可以提交，但只允许写入 name / body，不能自己把 approved 设成 true
create policy "public insert pending"
  on public.messages for insert
  with check (approved = false);
```

第二条策略是关键：访客无法伪造 `approved=true`，所以**任何留言都必须先经你手**才能公开。

> ⚠️ **表已经建过的话，别把上面整段重跑。** SQL Editor 是「一条失败、整段就停」：
> 开头的 `create table` 一撞上 `42P07 relation "messages" already exists`，
> 后面的 `alter table` 和两条 `create policy` **全都不会执行**。结果就是
> 一个很迷惑的状态 —— **表在，策略一条没有**：前台读出来是空的、提交报
> `42501 row-level security policy`。这时只跑下面这段，`drop policy if exists`
> 保证重复跑也不报错：

```sql
alter table public.messages enable row level security;

drop policy if exists "public read approved" on public.messages;
create policy "public read approved"
  on public.messages for select
  using (approved = true);

drop policy if exists "public insert pending" on public.messages;
create policy "public insert pending"
  on public.messages for insert
  with check (approved = false);
```

### 3. 填进配置
打开 `index.html`，改开头那段：

```html
<script>
  window.GUESTBOOK_CONFIG = {
    provider: 'supabase',
    supabaseUrl: 'https://xxxxxxxx.supabase.co',
    supabaseAnonKey: 'eyJhbGciOi...',
    table: 'messages'
  };
</script>
```

改完刷新页面，留言墙就会走真实后端了。

### 4. 日常审核
打开 Supabase 的 **Table Editor → messages**：

- 把某行的 `approved` 勾成 `true` → 刷新网站，这条就出现了
- 不想要的直接删掉 → 它从来没出现过

想更省事，可以在 Supabase 里建个 View 只看待审核的，或用它的 Dashboard 筛选 `approved = false`。

### 5. 建议再加的一道防线
前端已有：字数限制、30 秒冷却、机器人陷阱字段、昵称/内容必填。
若要更强的防刷，可开启 Supabase 的 **Auth → Rate Limits**，
或加一条基于 IP 的限制（需要走 Edge Function，属于进阶内容）。

### 6. 接完怎么自检

配置填好后，不用打开浏览器，三条 `curl` 就能判断问题出在哪一层
（把 `$U` / `$K` 换成你的项目地址和公开密钥）：

```bash
U=https://xxxxxxxx.supabase.co
K=sb_publishable_xxxx

# ① 表建了没、策略对不对：通的话返回 200 和 []
curl -s "$U/rest/v1/messages?select=name,body&limit=1" -H "apikey: $K"

# ② 不带钥匙应当被拒：返回 401 "No API key found"
curl -s "$U/rest/v1/messages?select=name" 

# ③ 能不能伪造已审核：应当被拒（42501 / row-level security）
curl -s -X POST "$U/rest/v1/messages" -H "apikey: $K" \
     -H "Content-Type: application/json" \
     -d '{"name":"x","body":"y","approved":true}'
```

对照着看返回码就知道卡在哪：

| 现象 | 说明 |
|---|---|
| `401 No API key found` | 密钥没带上，或 URL/密钥填错了 |
| `404 PGRST205 Could not find the table` | 第 2 步的 SQL 还没执行 |
| `200` 但返回一堆本该隐藏的留言 | 读策略没建对，`approved` 形同虚设 |
| ③ 返回 `201` | **危险**：写策略没拦住，任何人都能自己把留言设成已公开 |

## 方案 B：Giscus（不想自己维护数据库时）

留言存进你仓库的 **GitHub Discussions**，你在 GitHub 上审核，零后端。

1. 仓库必须是 **public**（你的 `AndySGZ.github.io` 已经是）。
2. 仓库 **Settings → General → Features** 勾选 **Discussions**。
3. 装 https://github.com/apps/giscus 这个 App，授权给你的仓库。
4. 打开 https://giscus.app ，填仓库名，选 Discussion 分类和映射方式，
   它会生成一段 `<script>`。
5. 把这段脚本贴进 `index.html` 留言墙区块，替换掉 `<form>` 和 `<ul data-guestbook-list>`。

代价：访客**必须有 GitHub 账号**才能留言，国内用户门槛较高。

## 方案 C：本机演示模式（当前默认）

`provider: 'local'` 时，留言只存在**你自己浏览器的 localStorage**，
别人访问你的网站看不到，只适合本地调样式用。

## 常见问题

**Q：为什么不用一个 JSON 文件存留言？**
写入 GitHub 仓库需要一个有写权限的 token。把这种 token 放进前端等于公开泄露，
任何人都能拿去改你的仓库。所以静态站点绝不能这么做。

**Q：换后端要重写前端吗？**
不用。`scripts/guestbook.js` 里只有 `load()` 和 `send()` 两个函数跟后端有关，
换服务商改这两个函数即可，界面、校验、渲染逻辑都不动。
